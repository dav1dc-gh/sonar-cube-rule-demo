# Security Rules — Path-Specific Instructions

## Context

This directory contains SonarQube rule definitions for **security vulnerabilities** — exploitable weaknesses that could allow attackers to compromise confidentiality, integrity, or availability. These are the highest-priority rules in the repository.

## Category Constraints

All rules in this directory MUST follow these constraints:

| Field | Required Value |
|-------|---------------|
| `type` | `VULNERABILITY` |
| `severity` | `CRITICAL` or `BLOCKER` (never MINOR/INFO for vulnerabilities) |
| `impacts[].softwareQuality` | Must include `SECURITY` with severity `HIGH` |
| `tags` | Must include `"security"` as the first tag |

## Severity Selection Guide

- **BLOCKER**: Direct data breach, credential exposure, or remote code execution (e.g., hardcoded-credentials, command-injection)
- **CRITICAL**: Exploitable vulnerability requiring specific conditions or user interaction (e.g., sql-injection, xss-vulnerability, open-redirect)

Never assign MAJOR, MINOR, or INFO to security vulnerabilities — if the issue isn't exploitable, it belongs in a different category.

## Tag Standards

Always include `"security"` as the first tag. Add relevant secondary tags from this approved list:

- `owasp-top-10` — maps to an OWASP Top 10 category
- `injection` — any injection-class vulnerability (SQL, LDAP, command, XSS)
- `authentication` — credential or session management issues
- `authorization` — access control bypass or missing checks
- `cryptography` — weak algorithms, key management
- `configuration` — insecure defaults or misconfiguration
- `data-exposure` — sensitive information leakage
- `input-validation` — missing or insufficient input sanitization

## Writing Security Rule Descriptions

Security rule descriptions must clearly articulate:

1. **What** the vulnerability is (the pattern detected)
2. **How** it can be exploited (attack vector)
3. **What** the impact is (data loss, privilege escalation, etc.)
4. **Where** it commonly occurs (frameworks, APIs, contexts)

Example: *"Detects SQL queries built via string concatenation with user-controlled input, enabling attackers to manipulate queries to extract, modify, or delete data."*

## Remediation Examples

Security remediation examples must show **defense-in-depth** — not just one fix, but the recommended secure pattern:

- Use parameterized queries (not just escaping)
- Use framework-provided security utilities (not custom sanitizers)
- Show the complete secure pattern (not just the changed line)

Keep `constantCost` realistic: most security fixes are `15min`–`30min` for straightforward parameterization, up to `2h` for architectural changes (e.g., implementing CSRF token infrastructure).

## Common Pitfalls When Creating Security Rules

1. **Don't confuse code smells with vulnerabilities.** If it's poor practice but not directly exploitable, it belongs in `code-smells/` or `maintainability/`.
2. **Don't set remediation cost too low.** Security fixes often require testing across multiple code paths.
3. **Always reference real attack patterns.** Descriptions should name the attack class (e.g., "SQL injection", "SSRF") for searchability.
4. **Include OWASP references where applicable.** Tag with `owasp-top-10` if the rule maps to a Top 10 category.

## Existing Rules Reference

This directory currently contains 28 rules covering: injection attacks (SQL, command, LDAP, XSS, log, XML), authentication/session issues (hardcoded credentials, insecure cookies, JWT misconfiguration), cryptographic weaknesses, access control (CSRF, missing authorization, mass assignment, CORS), input validation, resource consumption, and server-side vulnerabilities (SSRF, path traversal, open redirect, unsafe reflection, prototype pollution).

When creating new rules, check for overlap with existing definitions before proceeding.
