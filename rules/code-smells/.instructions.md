# Code Smells Rules — Path-Specific Instructions

## Context

This directory contains SonarQube rule definitions for **code smells** — structural quality issues that indicate poor design, accumulated technical debt, or violation of software engineering principles. These rules don't represent bugs or vulnerabilities but rather patterns that make code harder to understand, modify, and extend over time.

## Category Constraints

All rules in this directory MUST follow these constraints:

| Field | Required Value |
|-------|---------------|
| `type` | `CODE_SMELL` |
| `severity` | Typically `MAJOR` (design issues) or `MINOR` (stylistic concerns) |
| `impacts[].softwareQuality` | Must include `MAINTAINABILITY` (often `MEDIUM` or `HIGH`) |
| `tags` | Must include `"code-smell"` as the first tag |

## Severity Selection Guide

- **CRITICAL**: Severe structural issues that actively block development (extremely rare for smells — reserve for god-class-level problems in critical paths)
- **MAJOR**: Design violations that accumulate significant debt (e.g., god-class, duplicate-code, dead-code, feature-envy)
- **MINOR**: Stylistic or low-impact concerns that are easy to fix (e.g., magic-numbers in non-critical code)
- **INFO**: Suggestions or awareness-level findings (rare — most smells deserve at least MINOR)

## Tag Standards

Always include `"code-smell"` as the first tag. Add relevant secondary tags from this approved list:

- `design` — violates a design principle (SRP, OCP, DRY)
- `solid` — directly maps to a SOLID principle violation
- `maintainability` — impacts long-term changeability
- `complexity` — increases cognitive load or cyclomatic complexity
- `refactoring` — can be resolved through a named refactoring technique
- `error-handling` — relates to exception/error management patterns
- `debugging` — impacts ability to diagnose issues
- `coupling` — excessive dependencies between components

## Writing Code Smell Descriptions

Code smell descriptions should clearly articulate:

1. **What** the pattern is (the structural issue detected)
2. **Why** it's problematic (impact on maintainability, team velocity, bug risk)
3. **How** it manifests (concrete symptoms in the codebase)
4. **What principles** it violates (name the relevant design principle)

Example: *"Detects classes that have grown too large and handle too many responsibilities, violating the Single Responsibility Principle and making the code difficult to understand and maintain."*

## Remediation Examples

Code smell remediation should reference **named refactoring techniques** where applicable:

- Extract Method, Extract Class, Move Method (for god-class, feature-envy)
- Replace Magic Number with Named Constant
- Introduce Parameter Object (for long-parameter-list)
- Replace Conditional with Polymorphism

Show before/after at a conceptual level — the "after" should illustrate the target structure, not just a one-line fix.

## Remediation Cost Guidelines

Code smells often require more effort than simple bug fixes because they involve structural changes:

| Complexity | Cost | Examples |
|-----------|------|----------|
| Simple rename/extract | `5min`–`15min` | magic-numbers, empty-catch-block |
| Method-level refactoring | `20min`–`1h` | complex-methods, long-parameter-list |
| Class-level restructuring | `2h`–`4h` | god-class, feature-envy, duplicate-code |
| Architecture-level | `4h`+ | Only for cross-cutting concerns; rare |

## When to Use `params` (Configurable Thresholds)

Code smell rules frequently benefit from configurable thresholds since "too much" is subjective. Add `params` when:

- The rule detects quantity-based violations (lines, methods, parameters, nesting depth)
- Teams may reasonably disagree on the threshold
- The default might not suit all codebases

Common params for code smells:
- `maxLines` — for god-class, long-methods
- `maxParams` — for long-parameter-list
- `maxComplexity` — for complex-methods
- `maxDepth` — for nested structures

Always provide a sensible `defaultValue` backed by industry consensus.

## Boundary with Other Categories

Code smells can overlap with other categories. Use this decision tree:

- **Is it exploitable by an attacker?** → `security/`
- **Does it cause runtime failures or resource waste?** → `performance/` or use type `BUG`
- **Is it purely about readability/conventions/documentation?** → `maintainability/`
- **Is it a structural design issue?** → **This directory** (`code-smells/`)

## Existing Rules Reference

This directory currently contains 17 rules covering: complexity issues (complex-methods), design principle violations (god-class, feature-envy, refused-bequest, speculative-generality), duplication (duplicate-code, data-clumps), dead/unreachable code, error handling (empty-catch-block), parameter issues (long-parameter-list, primitive-obsession), encapsulation (message-chains), domain modeling (anemic-domain-model), and safety issues (null-pointer-dereference, unchecked-return-value, unsafe-concurrent-modification).

When creating new rules, verify the issue is truly a structural smell and not a bug, vulnerability, or readability concern better suited to another category.
