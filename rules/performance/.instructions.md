# Performance Rules — Path-Specific Instructions

## Context

This directory contains SonarQube rule definitions for **performance issues** — patterns that degrade throughput, increase latency, waste memory, or exhaust system resources. These rules protect runtime efficiency and operational stability.

## Category Constraints

| Field | Required Value |
|-------|---------------|
| `type` | `CODE_SMELL` (inefficient patterns) or `BUG` (causes outages/crashes) |
| `severity` | `CRITICAL` (service-impacting) or `MAJOR` (measurable degradation) |
| `impacts[].softwareQuality` | `RELIABILITY` (for BUG type) or `MAINTAINABILITY` (for CODE_SMELL type) |
| `tags` | Must include `"performance"` as the first tag |

## Type Selection: CODE_SMELL vs BUG

- **BUG**: The issue can cause service outages, OOM crashes, or data loss under load (e.g., memory-leaks, thread-pool-starvation, resource-leak)
- **CODE_SMELL**: The issue causes measurable inefficiency but won't crash the system (e.g., n-plus-one-query, string-concatenation-in-loop, unnecessary-boxing)

When in doubt, ask: "Can this bring down a production service?" If yes → `BUG`.

## Severity Selection

- **CRITICAL**: Can cause production incidents — pool exhaustion, thread starvation, memory leaks, unbounded growth
- **MAJOR**: Measurable performance degradation — N+1 queries, unnecessary object allocation, unoptimized regex

Never use MINOR/INFO for performance rules — if the impact isn't measurable, it doesn't belong here.

## Tag Standards

Always include `"performance"` first. Add from this approved list:

- `database` — query inefficiency, connection management
- `orm` — ORM-specific anti-patterns (lazy loading, N+1)
- `memory` — heap pressure, GC overhead, leaks
- `concurrency` — threading, pools, async violations
- `resource-management` — streams, connections, file handles
- `optimization` — general efficiency improvements
- `blocking` — synchronous operations in async contexts
- `availability` — issues that threaten uptime

## Writing Performance Rule Descriptions

Performance descriptions must specify:

1. **What** pattern is detected (the inefficient code structure)
2. **Where** it manifests (hot loops, request handlers, startup, etc.)
3. **How** it degrades performance (quantify when possible: "O(n²) instead of O(n)", "N+1 queries per request")
4. **What** the production impact is (latency spikes, memory exhaustion, thread starvation)

Example: *"Detects blocking calls such as Thread.sleep or CompletableFuture.get inside shared thread pools, which can exhaust all available threads and cause a full service outage."*

## Remediation Examples

Performance remediation must show the **efficient alternative**, not just "don't do this":

- Show the correct API/pattern (batch queries, try-with-resources, StringBuilder)
- Prefer framework-provided solutions over hand-rolled optimizations
- Include the performance characteristic change (e.g., "N queries → 1 query")

Remediation costs for performance rules:
- Simple API swap (StringBuilder, try-with-resources): `10min`–`20min`
- Query restructuring (N+1, batch operations): `30min`–`1h`
- Architectural fixes (thread pool isolation, async rewrite): `1h`–`4h`

## When to Use `params`

Add configurable params when:
- A threshold defines "too much" (e.g., collection size limit, loop iteration count)
- The performance sensitivity depends on the deployment environment
- Teams may tune detection aggressiveness

## Boundary with Other Categories

- **Causes data corruption or security breach?** → `security/`
- **Is poor structure but no runtime cost?** → `code-smells/` or `maintainability/`
- **Causes measurable runtime degradation or resource waste?** → **This directory**
