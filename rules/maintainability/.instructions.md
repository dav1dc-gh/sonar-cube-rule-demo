# Maintainability Rules — Path-Specific Instructions

## Context

This directory contains SonarQube rule definitions for **maintainability issues** — patterns that erode long-term code health, readability, and the ability to safely change code over time. These rules target the day-to-day friction that slows teams down.

## Category Constraints

| Field | Required Value |
|-------|---------------|
| `type` | `CODE_SMELL` |
| `severity` | `MAJOR` (structural issues) or `MINOR` (conventions/style) |
| `impacts[].softwareQuality` | Must include `MAINTAINABILITY` |
| `tags` | Must include `"maintainability"` as the first tag |

## Severity Selection

- **MAJOR**: Structural problems that compound over time — circular dependencies, hidden dependencies, shotgun surgery, mutable static state, deep nesting
- **MINOR**: Convention/style violations that reduce consistency — naming issues, missing documentation, excessive comments

CRITICAL is rare here — reserve for patterns that make entire modules untouchable. BLOCKER is never appropriate for maintainability.

## Tag Standards

Always include `"maintainability"` first. Add from this approved list:

- `readability` — impacts ability to quickly understand code
- `complexity` — increases cognitive load or decision paths
- `naming` — identifier clarity and consistency
- `conventions` — team/language style standards
- `design` — structural patterns and dependencies
- `cohesion` — scattered responsibilities
- `coupling` — excessive inter-module dependencies
- `testability` — patterns that make testing difficult
- `refactoring` — addressable via a named refactoring technique
- `documentation` — missing or misleading docs
- `concurrency` — thread-safety issues rooted in design
- `global-state` — shared mutable state problems

## Writing Maintainability Descriptions

Maintainability descriptions should explain:

1. **What** the problematic pattern is
2. **Why** it hurts maintainability (slower onboarding, higher change risk, test fragility)
3. **How** it manifests in practice (concrete symptoms developers notice)
4. **What** the fix direction is (named refactoring or principle)

Example: *"Detects mutable static fields that introduce global shared state, causing thread-safety issues, hidden dependencies, and making unit testing unreliable."*

## Remediation Examples

Maintainability fixes should reference the **design improvement**, showing the structural change:

- Extract interface/inject dependency (for hidden-dependencies)
- Introduce early return / guard clauses (for deep-nesting)
- Move method / extract module (for shotgun-surgery, circular-dependencies)
- Apply naming conventions consistently (for inconsistent-naming)

Focus on the "shape" of the fix rather than implementation details.

## Remediation Cost Guidelines

| Fix Type | Cost | Examples |
|----------|------|----------|
| Rename / reformat | `5min` | inconsistent-naming |
| Add documentation | `10min`–`15min` | missing-javadoc |
| Extract / restructure method | `15min`–`30min` | deep-nesting, too-many-parameters |
| Redesign dependencies | `30min`–`1h` | circular-dependencies, hidden-dependencies, shotgun-surgery |
| Eliminate global state | `30min`–`1h` | mutable-static-state |

## When to Use `params`

Maintainability rules frequently need thresholds:

- `maxDepth` — nesting level (deep-nesting)
- `maxParams` — parameter count (too-many-parameters)
- `maxLineCount` — method/class size (long-methods)
- `maxDependencies` — dependency fan-out

Always provide industry-standard defaults (e.g., max nesting = 4, max params = 5).

## Boundary with Other Categories

Decision tree:
- **Exploitable by attacker?** → `security/`
- **Causes runtime failures or resource waste?** → `performance/`
- **Violates a design principle (SRP, OCP)?** → Could be `code-smells/` if it's a named smell
- **Impacts readability, conventions, documentation, or safe changeability?** → **This directory**

Key distinction from `code-smells/`: Code smells are named anti-patterns from refactoring literature (god-class, feature-envy). Maintainability rules cover broader concerns — naming, docs, nesting, dependencies — that don't map to a single named smell.

## Existing Rules (15 rules)

Covers: readability (deep-nesting, excessive-comments, inconsistent-naming, long-methods), documentation (missing-javadoc), dependencies (circular-dependencies, hidden-dependencies), parameters (boolean-blindness, too-many-parameters), safety (missing-null-check, race-condition, swallowed-exceptions), state (mutable-static-state, hardcoded-urls), design (shotgun-surgery).

Check for overlap before creating new rules — in particular, distinguish from `code-smells/` rules covering similar territory (e.g., `code-smells/long-parameter-list` vs `maintainability/too-many-parameters`).
